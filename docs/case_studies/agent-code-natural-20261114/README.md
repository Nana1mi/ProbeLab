## 模型实际输出与验证反馈

大模型 Hint 的原文保存在 [hint.txt](hint.txt)。它建议预计算范数、使用 float64 的矩阵乘法、用 `argpartition` 获取 Top-K 后排序，并避免改变结果的低精度计算。它还猜测计时异常的原因，并建议同进程重复计时。这些只是模型意见：本实验的验证器使用独立子进程，实验并没有按 Hint 修改验证规则，也没有证据确认它对异常原因的猜测。

开发账本的反馈为：

> Rejected timing anomaly or speedup above the configured limit.

该签名既可能表示计时交叉校验失败，也可能表示速度超过 50 倍上限；仅凭保存的通用反馈，无法确定这次每个候选究竟因何被拒，更不能认定候选作弊。Solve 行以及最终行中的通用 `failure_signature` 可能沿用最近一次开发反馈，不能替代该候选或最终评测自身的证据。

开发阶段当前最优分数一直为 0.1，表示加速不足噪声阈值时的评分；最终 0.9284 是独立评测的时间比。不能将“0.1 → 0.9284”解释为性能提升。按控制器逻辑，没有被采纳的改进就保留初始实现，所以最终比较的是相同初始算法的独立测量，约 1× 的时间波动不代表新算法的收益。[retained_reference.py](retained_reference.py) 从对应源码提取，供查看最终保留的算法；它不是模型生成的优化代码。

## 自动摘要中的错误，复盘已纠正

1. 对话错误写成“强模型 9 次、小模型 0 次”。原账本 `cloud_calls=9, local_calls=0` 统计的是计费路由：两种模型都通过云 API 调用，不表示模型大小。实际执行路径为小模型 7 次、强模型 2 次，无本地 GPU。
2. Hint 行的 ¥0.021997 和 Solve 行的 ¥0.055349 均混合包含该轮小模型批次费用，不能当作强模型单独调用费用。当前记录不足以精确拆分大小模型各自费用。
3. 摘要把当前最优的约 1.04× 计时与失败候选联系起来，并猜测参考实现已经紧凑。这些说法缺乏逐候选证据，本复盘不采信。
