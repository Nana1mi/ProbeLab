# VELA 四分钟演讲 PPT 规划

交付范围：**六页 PPT 的制作规划与逐页讲稿**，用于后续制作正式幻灯片。本文件不是已生成的 `.pptx`。

总时长 **240 秒**。面向项目评委，先讲研究任务，再展示实际 Agent 行为，最后用独立对照案例支撑条件性的效果结论。项目统一名称：

**VELA**<br>
**Verifier-guided Exploration with Local and Cloud Agents**

核心讲述：小模型负责探索，大模型按需支援，验证器决定方案是否有效。当前已实现通用控制结构与三类预置任务；实验证据主要来自代码优化。模型参数、工具名和后端配置不放在演示任务输入中。

| --- | --- | --- | ---: | ---: |

## 第 1 页｜VELA：让模型围绕验证结果协作

**时间：0:00–0:20，20 秒。**

页面文字只保留：

> VELA<br>
> Verifier-guided Exploration with Local and Cloud Agents<br>
> 小模型负责探索，大模型按需支援，验证器驱动持续优化。

画面：左侧项目名与一句话定位；右侧用两个不同规模的抽象节点，与居中的验证节点构成循环。可沿用现有海报的配色与图形语言，但不整张缩放海报。演讲人、单位放底部。

讲稿：

> 大家好，我们的项目叫 VELA。它研究的是：面对需要反复试验的任务，怎样让小模型持续探索，在必要时请求大模型支援，再由程序验证结果。我们已经把这套过程做成了可以直接接收自然语言任务、并回看实验过程的 Agent。

转场：“首先看研究任务为什么需要这样的协作。”

## 第 2 页｜研究需要连续试错，也需要判断何时求助

**时间：0:20–0:55，35 秒。**

页面文字：

- 只用小模型：需要处理无效候选和搜索停滞。
- 每一步都用大模型：会持续消耗强模型调用。
- VELA：根据验证反馈决定继续探索还是升级支援。

画面：同一个任务框分别连到两条基线，再汇入中间的“按需协同”。不要画没有来源的成本下降曲线；此页讲机制动机，不展示效果数字。

讲稿：

> 我们关注的不是一次问答，而是需要不断生成方案、运行实验、再修改的研究过程。只用小模型，可能反复尝试却没有有效进展；每一步都交给大模型，又会持续消耗强模型调用。我们的切入点是，把自动验证作为协作依据：还有进展就继续探索，停滞之后再购买方向提示或完整方案。

转场：“这不是由模型口头判断成功，而是由验证器驱动。”

## 第 3 页｜小模型探索，停滞时升级，验证后采纳

**时间：0:55–1:40，45 秒。**

页面主图：

```text
用户研究任务
    ↓
小模型生成候选（可并行） → 格式／正确性／性能验证 → 采纳改进
    ↑                           ↓
    └── 根据反馈修改 ← 停滞时请求大模型 Hint / Solve
                                      ↓
                             独立最终评测与实验报告
```

图下三条说明：

- Hint 给方向，Solve 给完整候选；候选仍需验证。
- 开发反馈进入下一轮；最终评测不回流当前搜索。
- 输入、输出、验证、费用和停止原因都有记录。

讲稿：

> 系统首先让小模型生成候选，也可以扩大并行搜索。候选依次接受格式、正确性和性能检查，只有有效改进才会被保留。连续没有进展时，控制器升级到大模型：先请求方向提示，必要时再请求完整解答。大模型的输出同样需要验证。搜索结束后，还有独立最终评测，整个过程会保留模型任务、实际输出和验证证据，方便检查结果从哪里来。

页脚必须注明：**当前真实演示的两种模型均使用 API；本地 GPU 部署是支持的运行方式，尚未完成该硬件实测。**

## 第 4 页｜一句话任务，完整可回放的协同过程

**时间：1:40–2:30，50 秒。**

页面左上直接展示用户输入：

> 请优化批量余弦相似度 Top-K 检索算法。在保持结果正确的前提下，尽可能提高运行速度。

主画面：放 DeerFlow 原生协同卡片截图，突出“小模型 → Hint → Solve → 验证 → 最终评测”。不要把配置 JSON 作为主画面。

三个主指标：

| 独立最终加速比 | 小模型／大模型调用 | 研究 API 费用 |
| --- | --- | --- |
| **2.0454×** | **7／2** | **¥0.110530** |

边注：大模型 2 次为 Hint、Solve 各一次；Solve 方案被采纳。参考 0.3406 秒，候选 0.1665 秒。研究耗时 193.34 秒；费用含大小模型 API、不含聊天 Agent。

讲稿：

> 用户只需要给任务，不需要指定工具或调用顺序。这是实际运行的界面：小模型先探索，没有获得可采纳的改进，控制器依次请求了大模型的 Hint 和 Solve。Solve 产出的方案通过开发验证，最终独立评测得到约二点零五倍加速。页面上每一步都可以展开，看到原始输出、候选代码和验证反馈。这次实际调用了七次小模型和两次大模型。

演示方式：提前打开已经完成的对话，用 **10–15 秒**展开 Solve 的代码与验证证据，再回到 PPT。不要在四分钟现场等待这次约 193 秒的真实搜索；说明“这是已完成实验的回放”。网络不可用时使用截图和本地报告。

本页只证明**产品链路、真实协同与一次优化成功**，不证明优于单模型。首次验收中对话查询曾触发上游重复调用限制，后台研究继续完成；随后展示同一运行的报告。当前已改为长等待，原始记录保留。

## 第 5 页｜独立对照案例：更少强模型支出，更快的产出程序

**时间：2:30–3:30，60 秒。**

这是**另一组独立实验**，不能把本页的百倍加速与第 4 页的 2.0454× 画在同一条进展曲线上。第 4 页采用 50× 异常上限；本页三组统一采用 1000× 上限，允许正常 NumPy 候选参与比较。两组测量环境和验证设置不同。

页面主体用三行表格，保持列名完整：

| 策略 | 强模型调用 | 强模型费用¹ | 产出程序耗时中位数² |
| --- | ---: | ---: | ---: |
| 仅小模型 | 0 | ¥0 | 2.721 ms |
| 全大模型 | 6 | ¥0.028770 | 2.754 ms |
| VELA 协同 | **2** | **¥0.010876** | **2.393 ms** |

表格右侧只突出两项：

> 相比全大模型：**强模型费用 −62.2%**<br>
> 产出程序耗时：**−13.1%**

必须可读的页脚：

> ¹ 按“小模型本地部署、成本记零”假设，只计强模型费用；非本地 GPU 成本实测。<br>
> ² 一个代码任务、一个控制器种子；冻结候选后在 5 个输入上各复测 31 次，均通过被测输入的正确性比较。与上一页为独立实验。

讲稿：

> 协作是否值得，我们另外做了一组同任务、同控制器种子的三策略对照。固定每组搜索结束时保留的代码，再在五个输入上各重复测量三十一次。协同程序的耗时中位数是二点三九三毫秒，比全大模型产出的程序低百分之十三点一。在小模型成本记零的假设下，强模型费用从约二点八八分降到一点零九分，下降百分之六十二点二。这里比较的是产出程序的执行速度，不是 Agent 搜索速度；这是单案例结果，不能外推成平均优势。

讲者备注与问答数据：

- 仅小模型费用为零，协同不能声称比它更便宜；协同程序耗时比它低 12.1%。
- 原始双 API 费用：小模型组 ¥0.072515、全大模型 ¥0.028770、协同 ¥0.062252。若大小模型都按 API 收费，协同并不比全大模型便宜。
- 搜索耗时：小模型组 89.50 秒、全大模型 35.19 秒、协同 128.12 秒。本例没有证明协同搜索更快。
- 相同的是最多 6 轮、连续 4 轮无提升规则等设置；实际调用数不同，协同另有“咨询阶梯用尽”停止原因，已在原始账本保留。
- float32 在被测输入上正确，不代表所有近似相等相似度或极端数值都严格等价。
- 未做多次模型抽样统计或 Hint 的因果消融；不要使用“显著”“普遍”“全面优于”等结论。

## 制作和排练要求

- 主视觉使用现有 VELA 的暖白、深绿和少量铜色；一页一个结论。深色原始报告不直接铺满页面。
- 标题约 30–36 pt、正文 20–24 pt，方法和假设脚注至少 14–16 pt；数字保留单位及比较对象。
- 第 4 页不把完整聊天截图缩成小字，优先裁取原生协同卡片；完整截图和日志用链接作备查。
- 第 5 页图表如改为柱状图，零点一致，写清“程序耗时，越低越好”，费用图写清成本假设。
- 第 2 页结束应在 0:55、第 4 页结束应在 2:30。若超时，删减演示操作和讲者备注，不删成本假设。
